1. Business Requirements Document (BRD)

1.1 Project Overview

This document describes the Booking Management System built on top of the existing Node.js + Express.js + TypeScript Clean Architecture backend. The booking system allows customers to place service bookings via multiple channels (App, Website, Laptop CRM, WhatsApp-to-CRM, Phone Call), tracks the lifecycle of each booking from creation to completion or cancellation, and provides CRM admins with a complete view with search, filter, and pagination.

Design Philosophy
The booking system follows the same Controller → Use-Case → IDataServices → MongoGenericRepository → MongoDB pattern used throughout the backend. Adding a new module never breaks existing code — each module is a self-contained vertical slice.

1.2 Business Objectives

  • Multi-Channel Booking: Accept bookings from 5 channels — App, Website, Laptop (CRM), WhatsApp-to-CRM, and Phone Call.
  • Unique Identifiers: Every booking gets a human-readable, auto-incremented reference ID (DD-MM-YYYY-00001) for easy identification in CRM and communication with customers.
  • Branch-Level Support: Each booking is tagged to a branch (e.g., jalandhar), enabling multi-location support as the product scales.
  • Lifecycle Tracking: Booking status transitions are tracked — ongoing → completed / cancelled. Cancellations are logged with who cancelled and when.
  • Controlled Access: Normal users can only cancel their own booking. CRM admins (with API key) can edit any field, change any status, and delete records.
  • Audit Trail: Cancellation log array stores every status change with actor ID and timestamp — no data is ever silently overwritten.

1.6 Assumptions & Constraints

  • The system assumes the caller passes a valid user_id in the booking body — there is no foreign-key enforcement to the Users collection at the application layer (the two systems are loosely coupled by design).
  • Reference IDs are globally sequential, not per-day — the date in the ID reflects the booking creation date, not a day-specific counter.
  • The live_location_url field is optional; validation requires a valid URI if provided.
  • Soft delete (is_active = false) is used internally to filter default GET results; DELETE endpoint performs a hard (physical) delete.

Why an Array, not a single field?
A booking can theoretically be cancelled, re-opened, and cancelled again (by admin). An array retains the complete audit history. Each entry is immutable — we only ever $push to it, never overwrite.

2.4 Auto Reference ID — Algorithm Deep Dive

Why a Human-Readable ID?

MongoDB's default ObjectId (e.g., 664f1a2b3c4d5e6f7a8b9c0d) is not customer-friendly. When a CRM agent or customer support representative needs to reference a booking over the phone or in a WhatsApp message, a short, predictable ID like 03-05-2026-00042 is far easier to communicate and verify.

Format Specification

Reference ID Format
DD-MM-YYYY-SUFFIX

• DD-MM-YYYY = the date the booking was created (server time)
• SUFFIX = globally auto-incremented counter, formatted as follows:

   Counter 1 – 99,999   → 5-digit zero-padded: 00001 to 99999
   Counter 100,000+   → Letter + 4-digit: A0001, A0002 … A9999, B0001 …
Counter ValueSuffix ProducedFull Example
10000103-05-2026-00001
5000050003-05-2026-00500
99,9999999903-05-2026-99999
100,000A000103-05-2026-A0001
109,999A999903-05-2026-A9999
110,000B000103-05-2026-B0001

The letter prefix supports 26 letters × 9,999 values = 259,974 additional IDs beyond the initial 99,999 — a total of 359,973 unique IDs before overflow. A business generating 1,000 bookings per day would take nearly 360 years to exhaust this space.

The Counter Collection

The counter lives in MongoDB as a separate document in the counters collection:

{  _id: "booking_reference",
  seq: 42  // auto-incremented on every new booking
}

Why MongoDB $inc + upsert?

Two booking requests arriving at the same millisecond could both read the same counter value and produce a duplicate ID if we used a read-then-write approach. MongoDB's findOneAndUpdate with $inc is an atomic operation — the database guarantees that only one request gets each counter value, even under high concurrency.

// Atomic increment — SAFE under concurrent requests
const counter = await Counter.findOneAndUpdate(
  { _id: 'booking_reference' },
  { $inc: { seq: 1 } },      // MongoDB atomically increments seq
  { new: true, upsert: true }, // create the doc if it doesn't exist yet
);
// counter.seq is now UNIQUE for this request — no race condition possible

Suffix Formatting Algorithm

function formatCounter(seq: number): string {
  // Phase 1: 1-99999 → zero-padded 5 digits
  if (seq <= 99999) return seq.toString().padStart(5, '0');

  // Phase 2: 100000+ → letter prefix + 4-digit number
  const adjusted    = seq - 99999;                           // starts at 1
  const letterIndex = Math.floor((adjusted - 1) / 9999);   // 0=A, 1=B, 2=C …
  const num         = ((adjusted - 1) % 9999) + 1;         // 1-9999 within bucket
  return String.fromCharCode(65 + letterIndex) + num.toString().padStart(4, '0');
}
Beginner Explanation
padStart(5, '0') means: make the string exactly 5 characters long; if it's shorter, add zeros on the left. So 42 becomes "00042".

String.fromCharCode(65) = 'A', 66 = 'B', and so on. ASCII code 65 is the letter A in the international character standard.

3. Booking Status Lifecycle

3.1 Status State Machine

Every booking starts in ongoing status automatically on creation. It can then transition to one of three terminal states:

ongoing

The default state. Booking has been placed and is awaiting service delivery.

Set by: System (auto on creation)
completed

Service was successfully delivered to the customer.

Set by: CRM Admin only (requires API key)
cancelled_via_user

Customer cancelled the booking themselves through the app or website.

Set by: Customer (JWT only) OR CRM Admin (JWT + API key)
cancelled_by_admin_crm

CRM admin or agent cancelled the booking on behalf of the business.

Set by: CRM Admin only (requires API key)

State Transition Diagram

ongoing    ──────────────────────────────────────────
CRM Admin → (API key)
completed
User (JWT only) OR Admin
cancelled_via_user
CRM Admin → (API key)
cancelled_by_admin_crm
All three states are terminal — no further transitions allowed (enforced at business layer)

3.2 Cancellation Tracking & Audit Log

Whenever a booking status is changed to any cancelled value, the system automatically appends an entry to cancellation_log[] using MongoDB's atomic $push operator. This means:

  • You never lose old log entries — $push only adds, never replaces.
  • The caller does not need to manually send the log entry — the backend constructs it from the JWT payload and server clock.
  • You can see a full history: who cancelled, under what status, and exactly when.
// Booking PATCH: status → "cancelled_via_user"
// Body sent by user (no API key needed):
{
  "booking_status": "cancelled_via_user",
  "cancellation_reason": "Change of plans"
}

// What gets appended automatically to cancellation_log[]:
{
  "booking_status": "cancelled_via_user",
  "cancelled_by":   "<user_id from JWT>",  // never spoofable
  "cancelled_at":   "2026-05-03T10:30:00.000Z"
}

4.2 Conditional Auth — POST (booking_via)

The Business Reason

When a customer books via the App or Website, they are already authenticated via JWT — no additional API key is needed for that booking to be created. However, when a CRM agent creates a booking on behalf of a customer who contacted via WhatsApp, the action originates from a CRM tool (not from the customer's own session). This tool must identify itself with an API key, ensuring only authorised CRM agents can create such bookings.

App / Website / Laptop / Call — JWT only
  • Customer is authenticated with their own JWT
  • No API key header needed
  • Middleware skips API key check
  • Booking created with booking_via: "app" etc.
WhatsApp-to-CRM — JWT + API key
  • CRM agent is authenticated with JWT
  • CRM tool must send x-api-key header
  • Middleware runs full API key validation
  • Booking created with booking_via: "whatsapp_to_crm"

The Middleware Code

// conditional-api-key.middleware.ts
export function conditionalBookingCreateApiKey(req, res, next) {
  if (req.body?.booking_via === 'whatsapp_to_crm') {
    // CRM channel — run full API key validation (checks DB, expiry, usage limit)
    return apiKeyMiddleware(req, res, next);
  }
  // Self-service channel — skip API key, proceed directly to controller
  next();
}

4.3 Conditional Auth — PATCH (field-level)

The Business Reason

A regular customer should be able to cancel their own booking using only their JWT (no need to have an API key). But they should NOT be able to change operational fields like user_phone, address, branch, booking_via, or set an admin-only status like completed. Those changes are for CRM admins only.

The solution: check the PATCH body. If it only contains booking_status and/or cancellation_reason — no API key needed. If it contains anything else — API key is required before the controller is even reached.

// conditional-api-key.middleware.ts
const USER_ONLY_FIELDS = new Set(['booking_status', 'cancellation_reason']);

export function conditionalBookingPatchApiKey(req, res, next) {
  const bodyKeys    = Object.keys(req.body ?? {});
  const needsApiKey = bodyKeys.some(k => !USER_ONLY_FIELDS.has(k));

  if (needsApiKey) {
    // Admin field detected — API key must be validated before continuing
    return apiKeyMiddleware(req, res, next);
  }
  // Only user-facing fields — skip API key, let controller handle permission logic
  next();
}

4.4 How isApiKeyAuthenticated Flows Through the System

When the API key middleware successfully validates a key, it sets a flag on the request object:

// api-key.middleware.ts (after successful validation)
req.isApiKeyAuthenticated = true;  // typed in express.d.ts
next();

The booking controller reads this flag and passes it to the use-case as isAdmin:

// booking.controller.ts
const isAdmin = req.isApiKeyAuthenticated === true;
await bookingUseCase.updateBooking(id, value, isAdmin, req.user!.user_id);

The use-case enforces field-level and status-level permission checks based on isAdmin:

// booking.use-case.ts — field-level check
if (!isAdmin) {
  const attempted = Object.keys(dto).filter(k => !allowedKeys.has(k));
  if (attempted.length > 0) throw new AppError(`Permission denied — cannot update: ${attempted.join(', ')}`, 403);

  // Status check: user can only set cancelled_via_user
  if (dto.booking_status !== BookingStatus.CANCELLED_VIA_USER)
    throw new AppError('Permission denied — invalid status for non-admin', 403);
}

6. Search, Filter & Pagination

The GET /bookings endpoint uses MongoDB's $facet aggregation — a single database query that simultaneously returns both the paginated data slice and the total count. This is significantly more efficient than two separate queries.

How Search Works

// MongoDB $or query across 4 fields simultaneously
// ?search=nikhil  →  finds bookings where ANY of these match:
{
  $or: [
    { user_name:    { $regex: 'nikhil', $options: 'i' } },
    { user_phone:   { $regex: 'nikhil', $options: 'i' } },
    { user_id:      { $regex: 'nikhil', $options: 'i' } },
    { reference_id: { $regex: 'nikhil', $options: 'i' } },
  ]
}

How Date Range Works

// ?date_from=2026-01-01&date_to=2026-01-31
{
  createdAt: {
    $gte: new Date('2026-01-01'),
    $lte: new Date('2026-01-31T23:59:59.999Z') // includes full last day
  }
}

How Pagination Works ($facet)

// One MongoDB query, two simultaneous branches:
{ $facet: {
  data:       [{ $skip: 0 }, { $limit: 10 }],   // page 1 of 10 items
  totalCount: [{ $count: 'total' }]           // total matching documents
}}
// → { data: [...], totalCount: [{ total: 100 }] }
// → Response: { data, total: 100, page: 1, limit: 10, totalPages: 10 }

7. Frontend Integration Guide

7.1 Create a Booking (App/Website — JWT only)

The most common case: a logged-in user creates a booking from the mobile app or website. No API key is needed.

// React / JavaScript — Create booking from app
const createBooking = async (formData) => {
  const token = localStorage.getItem('jwt_token'); // or from cookie/Redux

  const response = await fetch('/api/v1/bookings', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${token}`,
      // No x-api-key header — not needed for app/website bookings
    },
    body: JSON.stringify({
      branch:       'jalandhar',
      user_name:    formData.name,
      user_id:      formData.userId,
      user_phone:   formData.phone,
      address:      formData.address,
      booking_via:  'app',             // or 'website'
    }),
  });

  const data = await response.json();
  // data.data.reference_id = "03-05-2026-00001" — show this to the user
};

7.2 User Self-Cancellation (JWT only — no API key)

When a user wants to cancel their own booking, they PATCH with just the two user-allowed fields.

// User cancels their booking — no API key needed
const cancelBooking = async (bookingId, reason) => {
  const response = await fetch(`/api/v1/bookings/${bookingId}`, {
    method: 'PATCH',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${token}`,
      // No x-api-key — only status + reason in body → no API key required
    },
    body: JSON.stringify({
      booking_status:      'cancelled_via_user',
      cancellation_reason: reason,
    }),
  });

  // Handle errors:
  // 403 → user tried to set a status other than "cancelled_via_user"
  // 404 → booking ID not found
};

7.3 CRM Admin Flow (JWT + API key)

CRM tools always send both headers. The CRM application stores the API key securely (environment variable, not in the frontend browser).

// CRM Admin — update any field
const adminUpdateBooking = async (bookingId, updateData) => {
  const response = await fetch(`/api/v1/bookings/${bookingId}`, {
    method: 'PATCH',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${adminToken}`,
      'x-api-key':     process.env.CRM_API_KEY, // stored securely in .env
    },
    body: JSON.stringify(updateData),
    // updateData can include: branch, user_phone, address, booking_status, etc.
  });
};

// CRM Agent — Create WhatsApp booking
const createWhatsAppBooking = async (customerData) => {
  const response = await fetch('/api/v1/bookings', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${agentToken}`,
      'x-api-key':     process.env.CRM_API_KEY, // required for whatsapp_to_crm
    },
    body: JSON.stringify({ ...customerData, booking_via: 'whatsapp_to_crm' }),
  });
};

Pro Tip — 401 vs 403
401 means "I don't know who you are" — the user needs to log in again.
403 means "I know who you are, but you're not allowed to do this" — do NOT log the user out. Show an appropriate message.

9. Scalability & Future Enhancements

9.1 Multi-Branch Expansion

The branch field is the foundation for scaling the product to new cities. Every booking is tagged with a branch name, enabling:

  • Branch-level filtering: GET /bookings?branch=delhi — already supported today.
  • Branch-level analytics: A future GET /bookings/analytics can group by branch with $group.
  • Branch-level access control: Add a branch field to the user/role and restrict CRM agents to their own branch.
  • MongoDB sharding: If volume grows, shard the bookings collection on branch to distribute load across nodes.

9.2 Ownership Check

Currently any authenticated user can GET any booking by ID. A common enhancement: verify that req.user.user_id === booking.user_id (or that the caller has an API key for admin override). This can be added to the use-case in one line without touching any other layer.

9.3 Booking Re-Open Flow

If the business needs a re-open flow (cancelled → ongoing), the booking_status field and cancellation_log[] already support this. A re-open log type can be added to the array and the state machine can be extended in the use-case — no schema migration needed.

9.4 Notifications

After createBooking in the use-case, a notification service call can be added to send a WhatsApp/SMS/email confirmation with the reference_id. Because the use-case is the single point of truth for booking creation, you only need to add the notification call in one place.

9.5 Reference ID Per-Branch

If each branch needs its own counter (e.g., JLD-00001, DEL-00001), the counter document key can be changed from "booking_reference" to "booking_reference_jalandhar". The reference_id format would become JLD-DD-MM-YYYY-00001 — a two-line change in generateReferenceId().

Architecture Decision Record
The booking system was designed as a completely independent vertical slice. Every other existing module (users, roles, modules, API keys, auth) continues to work exactly as before. The only shared infrastructure is the middleware chain and the data services abstraction layer — which is the whole point of Clean Layer Architecture.
